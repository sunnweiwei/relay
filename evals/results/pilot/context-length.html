Context-management methods by task context length

gpt-6-luna, medium reasoning effort, full-population runs on three benchmarks. Generated 2026-11-06. Only runs under one budget condition per benchmark are included; see evals/pilot/README.md for the protocol and its limitations.

1. Runs

  • BrowseComp-Plus: 4,950 ended runs of six methods; 43 task failures scored 0; 142 infrastructure failures excluded.
  • ARC-AGI-3: 133 ended runs of six methods; 0 task failures scored 0; 8 infrastructure failures excluded.
  • Terminal-Bench-Science: 337 ended runs of six methods; 3 task failures scored 0; 12 infrastructure failures excluded.
Context length. A run's unmanaged context length is the token count of Codex's own full history at the end of the run, before any method rewrites it: how long the context would be without context management. A task's context demand is the median unmanaged length of the five working methods on that task. Longer tasks also tend to be harder, so a falling curve mixes longer context with harder tasks; comparisons between methods on the same tasks are less affected.
Truncation fallback. All runs used Relay's common overflow fallback: when a method's own forced recovery still left a request over the window, Relay dropped the oldest tool call groups. ACM needed it in most runs, the other methods almost never (column "Runs with truncation fallback"). ACM's results therefore describe ACM together with this fallback.
RLM is not a measurement of the RLM method. Relay replaces the conversation with the RLM's handoff, and in many runs the main agent never sees the task (its final answer asks for the question). RLM is drawn for reference and is left out of the paired comparisons.
